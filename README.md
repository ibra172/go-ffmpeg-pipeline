# go-ffmpeg-pipeline

Асинхронный сервис обработки мультимедиа, написанный на Go: клиент отправляет задание на обработку видео (транскодирование, генерация превью или наложение водяного знака), сервис ставит его в очередь, рабочий процесс обрабатывает его в изолированном
режиме с помощью `ffmpeg`, и результат становится доступен, как только обработка завершена.

## Об этом проекте

Этот проект я делаю, чтобы на практике пройти через компоненты, из которых реально собирают асинхронные бэкенд-системы: проектирование HTTP API, очередь сообщений, воркер в отдельном изолированном процессе, аутентификация на сессиях, асинхронная оркестрация задач, контейнеризация и мониторинг.

## Архитектура

```
Client
  │
  ▼
RequestID middleware   (генерирует/пробрасывает request_id, кладёт логгер в context)
  │
  ▼
Logging middleware     (структурированные логи запроса через slog)
  │
  ▼
Panic middleware        (ловит паники и отправляет ошибки с кодом 500, предотвращая падение всего сервиса)
  │
  ▼
Router
  │
  ▼
Handler  →  Service  →  Repository (интерфейс)
                              │
                    ┌─────────┴─────────┐
                    ▼                   ▼
              in-memory (RAM)      PostgreSQL + Redis
              — сейчас              — в планах
```

Поток обработки задачи:

```
POST /task → задача сохранена (in_progress) → 201 Created сразу возвращается
                    │
                    ▼
          запуск ffmpeg (в фоне, отдельной горутиной)
                    │
                    ▼
          задача обновляется → ready / error
```

Трехслойная архитектура c раскладкой по фичам, а не по слоям — то есть не единые папки `handler/`, `service/`, `repository/` на весь проект, а у каждой фичи свои слои:

```
internal/
  features/
    task/
      handler.go              # HTTP-хендлеры: создать задачу, статус, результат
      service.go               # бизнес-логика, оркестрация фоновой обработки
      repository.go             # интерфейс (контракт)
      repository_ram.go         # in-memory реализация
      model.go                  # доменные типы: Task, TaskStatus, TaskResult
    auth/
      handler.go                # HTTP-хэндлеры: Register, Login
      service.go                 # регистрация, логин, работа с паролем и сессией
      user_repository.go          # интерфейс для хранилища User
      user_repository_ram.go      # in-memory реализация
      session_repository.go       # интерфейс для хранилища Session
      session_repository_ram.go   # in-memory реализация
      middleware.go               # middleware для аутентификации по токену
      model.go                    # доменные типы: User, Session
  apperr/                     # sentinel-ошибки
  ctxlog/                     # логгер в контексте запроса
  httpresp/                    # функции для JSON-ответов и ResponseWriter со статусом
  middleware/                 # RequestID, Logging, Panic
  config/                     # считывание конфигов
cmd/
  app/
    main.go               # composition root: сборка зависимостей, роутинг, graceful shutdown
    Dockerfile             # multi-stage сборка бинарника приложения
docs/                          # сгенерированная спецификация Swagger
Makefile                       # общие команды разработки  (run, test, build, ...)
```

Стоит отметить следующие проектные решения:

- **Repository за интерфейсом**. Сейчас всё хранится в RAM (хеш-таблица с мьютексом), но сервис работает с интерфейсом, а не с конкретной реализацией. Это позволяет менять форму хранилища данных без изменения сервисов и обработчиков.
- **Sentinel-ошибки** сопоставляются с HTTP-кодами статуса в одном месте, вместо того чтобы проверки `errors.Is` были разбросаны по всем хэндлерам.
- **Graceful shutdown** — `signal.NotifyContext` перехватывает `SIGINT/SIGTERM` и вызывает `http.Server.Shutdown`, который перестаёт принимать новые соединения и ждёт завершения активных хендлеров. Но обработка задачи запускается отдельной горутиной, которую сам HTTP-хендлер не ждёт т.к. он уже отправил 201 клиенту и завершился, а горутина может ещё продолжать работать. `Shutdown` про такие горутины ничего не знает, поэтому у сервиса есть свой `sync.WaitGroup`: сервис инкрементирует счётчик перед стартом фоновой обработки и ждёт его обнуления перед выходом из процесса.
- **Timing-safe login** — Если логина не существует, всё равно выполняется фиктивное сравнение хеша пароля, чтобы время ответа не отличалось от случая "логин есть, пароль неверный". Иначе по времени ответа можно перебором понять, какие логины вообще существуют в системе.

## Стек технологий

| | |
| --- | --- |
| Язык | Go 1.22+ (разработка на 1.25) |
| Роутинг | [`net/http`](https://pkg.go.dev/net/http) |
| Логирование | [`log/slog`](https://pkg.go.dev/log/slog) |
| Хеширование паролей | [`golang.org/x/crypto/bcrypt`](https://pkg.go.dev/golang.org/x/crypto/bcrypt) |
| Конфигурация | [`envconfig`](https://github.com/kelseyhightower/envconfig) |
| Документация | Swagger ([`swag`](https://github.com/swaggo/swag)) |
| Очередь *(в планах)* | RabbitMQ — между API-сервисом и воркером |
| Обработка медиа *(в планах)* | `ffmpeg`, запускается в изолированном Docker-контейнере на каждую задачу |
| Межсервисное взаимодействие *(в планах)* | gRPC — воркер сообщает API-сервису о завершении задачи |
| Хранилище *(в планах)* | PostgreSQL (пользователи, задачи), Redis (сессии) |
| Наблюдаемость *(в планах)* | Prometheus + Grafana |
| Оркестрация *(в планах)* | `docker-compose`, GitHub Actions CI |

## API

| Метод | Путь | Авторизация | Описание |
| --- | --- | --- | --- |
| POST | `/register` | — | Регистрация пользователя |
| POST | `/login` | — | Аутентификация, выдача Bearer-токена |
| POST | `/task` | Bearer | Отправить задачу на обработку |
| GET | `/status/{id}` | Bearer | `in_progress` / `ready` / `error` |
| GET | `/result/{id}` | Bearer | Получить результат обработки |
| GET | `/swagger/` | — | Интерактивная документация по  API |

Все защищённые маршруты ждут `Authorization: Bearer <token>`, полученный из `/login`.

### Конфигурация

| Переменная | По умолчанию | Описание |
| --- | --- | --- |
| `PORT` | `:8000` | Порт, на котором слушает HTTP-сервер |
| `SHUTDOWN_TIMEOUT` | `10s` | Максимальное время ожидания незавершенных операций при завершении работы |

## Основные этапы

- [x] **HTTP API** —  приём задач, статус, результат, in-memory хранилище за интерфейсом, Swagger документация
- [x] **Auth** — регистрация/вход, сессии с токенами Bearer, защищенные маршруты
- [ ] **Асинхронная обработка**
  - очередь RabbitMQ между API-сервисом и воркером
  - `ffmpeg`-воркер как отдельный микросервис
  - каждая задача обрабатывается в изолированном Docker-контейнере
  - воркер сообщает о завершении задачи по gRPC
  - `docker-compose` для совместного запуска API, воркера и RabbitMQ
  - CI на GitHub Actions
- [ ] **Продакшн-хранилище & мониторинг**
  - PostgreSQL для пользователей и задач, Redis для сессий
  - метрики Prometheus: длительность обработки, какая операция/фильтр использовались
  - дашборд Grafana поверх этих метрик
